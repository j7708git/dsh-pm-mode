# pm-intake — 需求訪談與規格化

## 什麼時候用
使用者提出新需求、新專案、新功能或要改範圍時。這是**流程第一步**。

## 鐵則
1. **未取得使用者對規格的確認，不得動工**：不建專案、不寫程式、不派實作 subagent。（唯讀研究可以先做。）
2. **一次最多問 3 個問題**，每題都要附上你建議的答案，第一個選項標「（推薦）」。
3. **不要問技術問題**（用什麼語言、框架、資料庫、要不要用 API）。技術選擇由你決定，並在規格裡寫明選擇與白話理由。
4. 使用者答不出來時，**提供具體畫面或例子**，不要追問抽象名詞。例：「你希望一打開就看到什麼？例如：這個月總共花了多少。」
5. 使用者說不清楚的地方，寧可先寫成「暫定」並標記，也不要卡住不動。

## 步驟
1. 讀使用者的訊息，分成三欄：**已知**、**未知但會改變做法**、**未知但不影響做法**。只問第二欄。
2. 用 `ask_user_question` 問 ≤3 題（每題 2–4 個選項，附推薦）。
3. 判斷規模：
   - **小型**（半天內、單一腳本或單頁面）→ 規格用簡短版：目的／做法摘要／驗收 3 條。
   - **中大型** → 用下方完整模板。
4. 寫 `docs/01-需求規格.md`（先確認 `docs/` 存在；不存在就建立）。
5. 用**三句白話**向使用者摘要規格，並用 `ask_user_question` 問：「這樣對嗎？可以開始嗎？」（選項：可以開始（推薦）／我要修改）。
6. 只有得到「可以開始」才進入 `pm-scaffold`。若使用者要修改 → 改文件、重新確認，並把決定記到 `docs/04-進度日誌.md`。

## 規格模板（`docs/01-需求規格.md`）
```markdown
# 需求規格：<專案／功能名>
- 日期：<YYYY-MM-DD>
- 版本：v1
- 狀態：待使用者確認 / 已確認（YYYY-MM-DD）

## 1. 一句話目的
<用白話說：這是給誰、解決什麼問題>

## 2. 使用情境
- 當我 <做什麼>，我應該看到 <什麼結果>
- （至少 2 條）

## 3. 必須有的功能
| # | 功能 | 白話說明 | 優先 |
|---|---|---|---|
| F1 | | | 必須／加分 |

## 4. 驗收標準（可被外人重複驗證）
- [ ] 當我 ……，我應該看到 ……
- [ ] 邊界：輸入空白／錯誤資料時，應該 ……
- [ ] 資料保存：<會不會存檔、存哪裡、重開還在嗎>

## 5. 不做什麼（範圍外）
- <明確排除，避免日後爭議>

## 6. 風險與假設
- 假設：……
- 風險：……（白話說明如果錯了會怎樣）

## 7. 技術附錄（給實作者，使用者可略過）
- 選型：<語言／框架／套件>，理由：一句話
- 預期檔案結構：<簡圖>
- 需要的環境：<例：node 24、git>
```

## 品質檢核（寫完規格後自己跑一次）
- [ ] 問題 ≤3 題，且每題都有建議答案
- [ ] `docs/01-需求規格.md` 已寫，含「不做什麼」
- [ ] 驗收標準每一條都能被外人重複驗證（不是「感覺良好」）
- [ ] 使用者已明確回覆「可以開始」
- [ ] 文件裡沒有未解釋的技術名詞（技術附錄除外）

## 常見錯誤
- ❌ 一次丟 8 個問題給使用者 → 改成 3 題，其餘用「暫定」並在規格標記。
- ❌ 使用者說「隨便」就自己放大範圍 → 縮到最小可用版本（MVP），並在規格寫「第一版只做 X」。
- ❌ 直接開工 → 違反鐵則 1。
